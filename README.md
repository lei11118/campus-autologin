# 校园网自动认证（常驻守护版）

> 📦 **下载**：到 [Releases](https://github.com/lei11118/campus-autologin/releases/latest) 下载 `campus-autologin-setup-v1.2.1.exe`（自解压一键安装）或便携 zip。
>
> 💡 如果拿到的是 **`campus-autologin-setup-*.exe`**：直接双击，它会自动解压到
> `%LOCALAPPDATA%\campus-autologin` 并立刻启动安装向导（解压不需要管理员；
> 只有注册开机任务那一步会弹 UAC）。本文档描述的是**解压之后**的目录用法。

开机后自动判断校园网是否需要认证，需要就自动登录；**掉线秒级自动重连**。
**支持「无人登录 Windows」的无人值守模式**，适合把机器放在宿舍/机房，靠远程控制随时连回来。

- **零第三方依赖**：纯 Python 标准库 + Windows DPAPI（不需要 pip install 任何东西）
- **零配置迁移**：整个目录拷到别的机器就能用；门户地址自动发现，不用手填内网 IP
- **常驻守护**：一个常驻进程 + 一个看门狗，开机即拉起，平时几乎不占资源（实测 **CPU ≈0.05% 单核 / 内存 ~35MB**）
- **版本**：v1.2.1 · 标记 ID `CAMPUS-NET-AUTOLOGIN`

> 已在 GiWiFi「校园助手」gportal 门户（`/gportal/web/login` + `authLogin`）上实机验证：
> 字节级复刻前端加密、SYSTEM 身份下完成真实认证、掉线自动重连。
> 其他厂商（深澜 Srun / 锐捷 ePortal / Drcom）门户结构不同，需按第五节适配。

## 一、它是怎么"一直盯着网络"的

```
Windows 开机
 │
 ├─ 计划任务 GiWiFi-Campus-AutoAuth（SYSTEM 身份，无需任何人登录）
 │     └─ 开机 30 秒后拉起【常驻守护进程】—— 之后它就一直活着
 │          循环：探针 → 在线就睡 25 秒 → 掉线立刻认证 → 复核 → 继续
 │          失败退避 5→10→20→30→60 秒（封顶 60s 循环重试，**永不长时间停摆**）
 │
 └─ 计划任务 GiWiFi-Campus-AutoAuth-Watchdog（每 5 分钟）
       └─ 看守护进程还活着吗？心跳过期/进程没了 → 杀掉重拉（自愈）
```

**为什么敢说"不会长时间掉线"**（这是踩过的坑）：

| 旧做法 | 问题 | 现在 |
|---|---|---|
| 计划任务每分钟拉一个进程检查一次 | 进程创建频繁；掉线最坏 1 分钟才恢复 | 常驻进程，在线 25s / 掉线 2~5s 一次探针 |
| 连续 3 次失败 → 冷却 30 分钟 | **实测翻车**：服务端返回 `终端已认证` 被误判成密码错误，直接把自己锁 30 分钟，明明能重连却干等 | **取消长时间冷却**：只有真正的账号/密码类错误才放慢到每 10 分钟重试一次；其余一律快速退避重试 |
| 每分钟写一行"无需认证"日志 | 日志每天膨胀上千行 | 只在**状态变化 + 每次认证结果 + 每 30 分钟心跳**时写，日志缩到 1/30；单文件超 2MB 自动轮转 |
| 只看进程在不在 | 普通用户无权探测 SYSTEM 进程，会把正常工作的守护进程误判成"已死"并**重复拉起** | 以**心跳文件**为准（守护进程每轮自己写），无权探测也能正确判断 |
| 认证成功后只等 1.5 秒就复核 | **最致命的一坑**（2026-10-14 实测：一天被锁 8 次、断网 8 小时）——AC 放行要 10~30 秒，等不到就判"复核未通" → 计入失败 → 30 分钟冷却，**明明登录成功却干等半小时** | 复核改为最多等 **25 秒**；而且只要接口已报成功，**一律不计失败**（v1.2.1） |

## 二、安装（双击一个文件）

**双击 `安装.bat`**，按提示输入：

| 提示 | 输入 |
|---|---|
| `[1/4]` 算法自检 | 等它出 `[OK]` |
| `[2/4]` 运行模式 | **回车** = 开机即认证（无人值守，推荐）；输入 `2` = 仅登录后认证 |
| `[3/4]` 账号/密码 | 输校园网账号 → 输密码（不回显）×2 → 保存方式**回车**（推荐默认） |
| `[4/4]` 安装任务 | 若弹出 **UAC 窗口点「是」**；随后它会拉起守护进程并打印验证结果 |

看到下面这几行就算成功：

```
[OK] GiWiFi-Campus-AutoAuth（daemon）
[OK] GiWiFi-Campus-AutoAuth-Watchdog（watchdog）
验证通过：守护进程已由计划任务拉起。
```

## 三、运行模式

| | 常驻守护 `[1]`（默认） | 仅登录后 `[2]` |
|---|---|---|
| 运行身份 | **SYSTEM** | 当前登录用户 |
| 启动时机 | **开机 30 秒后** | 用户登录后 30 秒 |
| 巡检节拍 | 在线 25 秒 / 掉线 2~5 秒 / 失败 5→60 秒退避 | 每 5 分钟一次 |
| 需要人登录 Windows | **不需要** ✅ | 需要 |
| 需要管理员 | 需要（一次性 UAC） | 不需要 |
| 自愈 | 看门狗每 5 分钟兜底 + 任务自带失败重启 | 无 |

> 关键区别：`[2]` 的任务**在没人登录时根本不会触发**。做远程控制一定选 `[1]`。

**密码保存方式**（无人值守必看）：

| 选项 | 说明 | 无人值守可用？ |
|---|---|---|
| **[1] 明文 + 文件权限锁定**（默认） | 最可靠；文件权限收紧到「你 + SYSTEM + Administrators」 | ✅ |
| [2] 机器范围 DPAPI 加密 | 加密存储，本机进程（含 SYSTEM）都能解 | ✅ |
| [3] 用户范围 DPAPI 加密 | 最安全，但**只有你登录 Windows 后**才解得开 | ❌ 无人值守别选 |

## 五、换到别的学校 / 别的门户怎么办

**门户地址不用配**：未认证时随便访问一个 http 站点，认证设备(AC)会把你 302 到门户登录页，
程序从中自动读出门户 IP、登录页路径、认证接口路径（只在目标像内网 IP 或含 portal/wifi/srun
等特征时才采纳，避免被普通网站跳转骗到）。想固定写死就在 `config.json` 里填 `portal`。

**如果对方不是 GiWiFi gportal 家族**（例如深澜 Srun、锐捷 ePortal、Drcom），认证接口与加密方式不同，
需要按对方门户页面改三处：

1. `portal_path` / `auth_path`：登录页与认证接口路径；
2. `encrypt_key`：门户前端 JS 里 `CryptoJS.AES.encrypt(...)` 的 key
   （本工具实现的是 `AES-128-CBC + ZeroPadding`，iv 由登录页下发）；
3. 若是完全不同的接口形态（比如锐捷的 `InterFace.do?method=login`），改 `do_login()` 里的请求构造。

排查方法：浏览器打开门户页 → F12 → Network，点一次登录，看那条 XHR 的 URL 和 Form Data；
再看页面 JS 里怎么加密这些参数的。

## 六、工作原理（GiWiFi gportal 家族）

```
判断是否需要认证
  GET http://nettest.gwifi.com.cn  -> {"resultCode":0,"data":"\"\""}   => 已在线
  GET http://connect.rom.miui.com/generate_204 -> 204                 => 已在线
  被 302 到门户 / 探针不通                                            => 需要认证 / 无法判断

认证
  1. GET 门户登录页 -> 解析服务端下发的隐藏参数(iv/sign/nasName/userIp/pid...)
  2. 明文 = 表单字段按 jQuery.serialize() 拼串（encodeURIComponent + "&"）
     密文 = AES-128-CBC(key=门户前端硬编码, iv=页面下发, ZeroPadding) -> Base64
  3. POST /gportal/web/authLogin?round=<随机数>   体: data=<Base64>&iv=<iv>
  4. 成功判据 status==1，随后再用探针复核一次
```

内置的可靠性设计：

- 探针**重试 3 次 + 交叉验证**后再判定"需要认证"，避免瞬时抖动误判
- 开机时若网络还没就绪，最多等 60 秒再判断
- 认证接口报错但探针显示已在线 → 判定为无需认证（多设备/已在别处登录）
- **失败分类**：`reasoncode 16/32/40/41` 或明确"密码错误/账号不存在"才算账号类问题；
  `终端已认证` 这类 AC 侧会话冲突按瞬时问题快速重试
- 每次认证都会在日志里打印**运行身份 + 密码来源与可用性**，出问题一条 grep 就能定位

## 七、排障

日志：`logs\autologin-YYYYMMDD.log`（UTF-8；超 2MB 自动轮转为 `.log.1`）

| 日志里看到 | 含义 / 处理 |
|---|---|
| `守护进程启动 (PID ...，身份 SYSTEM（服务账号·无需任何人登录）)` | 无人值守链路正常 ✅ |
| `启动检查：网络正常` / `网络已恢复正常` | 一切正常 |
| `检测到需要认证` + `认证成功` | 刚自动登录成功 |
| `... 秒后重试（连续第 N 次失败，不会长时间停摆）` | 认证暂时失败，正在快速退避重试 |
| `认证接口返回成功，但复核仍未通网（AC 放行延迟，不计失败）` | 正常现象：登录其实已成功，AC 还在放行中，几秒后自动恢复 ✅ |
| `判定为账号/密码类问题，改为每 10 分钟重试一次` | 账号或密码有问题 → `--set-password` 重设 |
| `无法判断联网状态` | 不在校园网内 / 网线没插 / DHCP 没拿到地址 |
| `密码解密失败` | 存的是**用户范围** DPAPI 而任务以 SYSTEM 运行 → 重设密码并选 [1] 或 [2] |
| `准备阶段失败：未能确定门户地址` | 不在校园网内 |
| `看门狗：未发现存活的守护进程，正在拉起 ...` | 守护进程曾退出/卡死，看门狗已自动恢复 ✅ |
| `守护进程 PID x 心跳已 N 分钟没更新（判定卡死），强制重启` | 同上，进程假死被强杀重拉 ✅ |

```bat
:: 看守护进程与看门狗状态（推荐用这个）
python giwifi_auth.py --status

:: 或直接看计划任务（管理员身份能看到看门狗任务的细节）
schtasks /Query /TN GiWiFi-Campus-AutoAuth /V /FO LIST
schtasks /Query /TN GiWiFi-Campus-AutoAuth-Watchdog /V /FO LIST
```

> 提示：以 SYSTEM 身份注册的任务，**普通用户身份可能查询不到**（报"拒绝访问"）。
> 这不是没注册上，用管理员身份运行 `--status` 即可确认。

## 八、无人值守（远程控制）注意事项

- **电源计划里把"睡眠"设为「从不」**，否则机器睡了网络就断，远程连不进来。
- 校园网若限制"同账号在线设备数"，本工具会持续把本机抢回来。
- 目录被计划任务按**绝对路径**引用：**移动/改名本目录后，必须在新位置重跑一次
  `python giwifi_auth.py --install`**（标记文件里也写了这条）。
- 换 Windows 用户或换机器后，DPAPI 密文解不开（若你选了加密保存）→ 重新 `--set-password`。
- 想彻底停掉：`卸载.bat`（会删掉两个任务并停止守护进程）。
